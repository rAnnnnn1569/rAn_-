# 车载录像「打不开」排查：MPEG-PS 冒充 MP4

> 现象：平台导出的车载录像，文件名是 `.mp4`，**Windows 自带播放器与微信内置播放器都打不开**（报 `0xC00D36C4`），但 PotPlayer 能播。
> 结论：**文件内容根本不是 MP4** —— 是 MPEG-2 PS 封装 + G.711 音频。转封装即可解决。

---

## 一、定性第一步：错误码先分层

媒体基础库的错误码不是都指同一件事，先分开：

| 错误码 | 含义 | 指向 |
|---|---|---|
| `0xC00D5212` | `MF_E_TOPO_CODEC_NOT_FOUND` | **缺解码器**（装 HEVC 扩展可解） |
| **`0xC00D36C4`** | **`MF_E_UNSUPPORTED_BYTESTREAM_TYPE`** | **字节流类型不受支持 → 连容器都没认出来** |

⇒ 本例是后者：**不是「缺解码器」，是解析器根本没把它当 MP4**。方向应该往容器上查，而不是去装解码器。

**为什么 PotPlayer 能播**：它内置 FFmpeg，解析器极其宽容，能"猜"出非标格式。**能播 ≠ 文件正常。**

---

## 二、查证：三组独立证据互证

### 2.1 技术链

```
错误码分层（先判断"是解码器还是容器"）
   → 魔数嗅探（看文件头前 4 字节是什么）
   → 容器解析（真 MP4 看 box：ftyp / moov / mdat / stsd）
   → 编码解析（video fourcc + audio codec）
   → 出修复命令
```

### 2.2 三组证据

| 证据源 | 结果 | 判定 |
|---|---|---|
| **文件头十六进制** | `00 00 01 BA` | 这是 **MPEG-2 PS 的 pack header**，不是 MP4 的 `....ftyp` |
| **PS 流表解析** | 视频流 ID `0xE0`、音频 `stream_type=0x90`（G.711 私有流） | 与文件头吻合 |
| **播放器文件信息** | 源滤镜显示 `Built-in MPEG2 PS Source`；`Video #1 ID: 224 (0xE0)` | 第三方工具独立得出同一结论 |

三条对上，诊断闭合。

### 2.3 ffprobe 读出的具体参数

| 项 | 值 |
|---|---|
| 容器 | `format_name=mpeg`（MPEG-PS） |
| 视频 | `h264 (High) 1280x720 @25fps` → **可 `-c:v copy` 直拷** |
| 音频 | **`pcm_alaw`（G.711A）8kHz 单声道** |
| 起始时间戳 | **非零**（存在终端开机计时残留，导致 seek 异常 / 卡顿） |

> ⚠️ 多个下载副本格式完全一致 ⇒ **不是单个文件损坏，是导出格式本身如此**，属系统性问题。

---

## 三、根因（两层，缺一不可）

1. **容器层**：MPEG-2 PS 冒充 MP4。PS 属 MPEG-1/2 复用体系，没有 MP4 的 `ftyp` / `moov` 结构。
2. **音频层**：**G.711 在 MP4 里非法**。即使把 PS 重封装成 MP4，音频也必须换掉 ⇒ **绝对不能只做 `-c copy`**。

**附带故障**：起始时间戳非零导致 seek 异常；转封装后会自动归零。

---

## 四、处置

### 4.1 转封装命令（已实测）

```bash
ffmpeg -i "输入.mp4" -c:v copy -c:a aac -b:a 64k -movflags +faststart "输出.mp4"
```

- `-c:v copy` ⇒ **视频轨直拷，画质零损失、秒级完成**（转码日志可见 `Stream #0:0 -> #0:0 (copy)`）
- `-c:a aac` ⇒ 音频必须转（G.711 不被 MP4 接受）
- `-movflags +faststart` ⇒ `moov` 前移，微信 / 网页可边下边播

**降级备选**（万一 copy 失败）：`-c:v libx264 -preset veryfast -crf 23`

### 4.2 输出校验（转完必须验）

| 检查项 | 期望 |
|---|---|
| 文件头 | `....ftyp`（ISO-BMFF） |
| box 顺序 | `moov` 在 `mdat` **之前**（faststart 生效） |
| 视频 fourcc | `avc1` |
| 音频 | `mp4a`（AAC-LC） |
| 起始 PTS | `0.000000` |

### 4.3 批量处理建议

同一批下载里常有重复副本（同一段录像被下了多次）。先按 **MD5 去重**再转，能省掉大半工作量。

## 五、概念澄清：`H.264` vs `avc1`

**两者不是两种编码，是同一件事的两个层面。**

| | 是什么 | 在哪一层 |
|---|---|---|
| **H.264** | 视频**编码标准**（ISO-IEC 14496-10，即 AVC） | 码流层 |
| **`avc1`** | MP4 容器里的 **fourcc**（video sample entry 的 4 字符标识） | 封装层 |

- 同一个 H.264 码流，装进 MP4 就叫 `avc1`，装进 AVI 里可能叫 `H264`。**没有「H.264 转成 avc1 编码」这种操作，只有改标签或换封装。**
- **只要 remux 进 MP4，tag 自动就是 `avc1`** —— 它是副产品，从来不是独立问题。
- 🔴 **不要用十六进制编辑器直接改 `stsd` 里那 4 个字节** —— 手工改不会同步 `avcC` box 和长度字段，必然产出破损文件（比现在还糟）。

**只改 fourcc 的命令**（文件已在 MP4 内、标签非标时用，不碰音频）：

```bash
ffmpeg -i "in.mp4" -c copy -tag:v avc1 "out.mp4"
```

> 边界：`avc3` 把 SPS/PPS 放在**码流内**，`avc1` 要求放在 **`avcC` box** 里。若源头是**严格 avc3**，单纯 `-tag:v avc1` 可能产出"标签是 avc1 但 avcC 缺 SPS/PPS"的文件。遇到这种情况应重编码，而不是改 tag。

## 六、给平台方 / 终端厂商的反馈口径

**这是导出链路的产品缺陷**，不是单台终端偶发问题。合理需求是**导出时直接按标准 MP4 封装**（H.264 + AAC + `moov` 前置）。

**进一步追责前，先分清文件是从哪条链路产出的**（这一步跳过会归错责任方）：

| 下载方式 | 文件怎么来的 | 封装责任方 |
|---|---|---|
| **FTP 下载** | 终端写好 → FTP 推平台存储 → 原样给用户 | **终端 / 设备厂家** |
| **视频播放下载** | 平台下发回放指令 → 流媒体服务器抓流落盘 | **平台侧** |

**特征指纹**（供初步判断，属机制推断，需实测确认）：

| 特征组合 | 指向 |
|---|---|
| **PS 容器 + G.711 音频** | 平台**抓流件** —— 音视频流本身不含 AAC（终端音频编码为 G.711 系列），抓流写盘必然是 G.711，容器按 PS 复用也常见 |
| **MP4 容器 + AAC 音频** | 终端**写件**（FTP 上传） |

**验证方法（10 分钟，务必做）**：同一辆车、**同一时间段**，两种下载方式各下一份，比对容器与音频编码。

- 两种方式产物格式不同 ⇒ **平台侧问题**，与终端厂家无关；
- 两种方式都出 PS ⇒ 才轮到终端 / 厂家。

> **别用「能播」反推「合规」**：能否播放是结果，是否合规要看标准原文。合规判断必须落到条款上。

## 七、判定速查表

| 看什么 | 正常 | 异常 |
|---|---|---|
| 文件头 4 字节 | `....ftyp` | `00 00 01 BA`（PS） |
| 容器 | ISO-BMFF MP4 | MPEG-PS |
| video fourcc | `avc1` | 其他 |
| audio | `mp4a`（AAC） | `pcm_alaw` / `G.711` |
| 起始 PTS | `0.000000` | 非零（seek 异常） |

**30 秒自查法（PotPlayer，不用装工具）**：打开视频 → 右键 → 属性 → 文件信息，只看两处：

1. **`Format` 字段**：`MPEG-4` = 正常；`MPEG-PS` = 包装不对
2. **`Audio` 子项**：`AAC` = 正常；`G.711 / PCMA / PCMU` = 不合规

命中任一条 → 套用 §4.1 的转封装命令。

> ⚠️ 注意 `Format` 字段判的是**容器**，不是编码。编码要看 `Codec ID` 或 `Video #N` 子项。

## 八、本次踩到的概念修正

**MPEG-PS 不是「裸流」。**

- **裸流 = ES（基本流）**：只有一路编码数据本身，没有复用层、没有时间戳、没有流标识（如 Annex-B 裸 H.264、ADTS 音频）。**一个裸流只能装一路东西。**
- **PS 有完整复用层**：pack 头、PES 包（带 `stream_id`）、PTS/DTS 时间戳、SCR 系统时钟。本例文件同时装了视频与音频两路，还带一个私有 `stream_type` —— 裸流装不下这些。
- PS 与 TS 是同一层的两个兄弟：**TS 面向传输**（高误码，广播用），**PS 面向存储**（低误码，本地录像用）。TS 同样不是裸流。
- 准确说法：**PS 是个轻量容器** —— 相对 MP4 少了全局索引（无 `moov` / sample table），seek 只能靠扫描，容错性好但随机定位差。
