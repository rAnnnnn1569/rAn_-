# 服务"重启无效"类故障排查方法论

> 适用场景：服务**能启动、重启也不报错**，但功能就是不对（批量任务全失败、数据对不上、状态卡住）。
> 这类故障比"服务起不来"更难，因为**没有任何明显报错指向原因**。

---

## 一、先讲一个最容易走偏的直觉

遇到功能异常，第一反应往往是"重启试试"。重启后还是不对，很多人就开始在**环境层面**乱试（重装、改配置、回滚版本）。

**但有一类问题的根因根本不在服务状态，而在"服务调用的外部接口/传参方式变了"**——服务本身运行得好好的，它是被对端拒绝的。

**判断信号**：**重启无效 + 服务进程健康 + 日志说"调用完成"但业务结果为零**。

这三个条件同时出现，基本可以判定：**问题在代码/接口层，不在服务状态层**。

---

## 二、标准排查路径（五步）

```
① 重启无效        →  不再在"服务状态"上打转
② 查业务成果表    →  用 SQL 按状态字段分组统计，确认"是一辆都没成功，还是部分成功"
③ 认准"业务模块自身日志" →  ⚠️ 不要只看门户/调度器日志（它只写"调用完成"）
④ 手动复现接口    →  curl 直接打接口，区分"地址不通"和"传参格式不对"
⑤ 锁定根因并回填  →  修正调用方式，重启验证业务成果
```

### 关键在第 ③ 步：日志要"认对"

一次真实案例：门户页面显示"共 2,700 余条，成功 0 条"，页面"已处理数"始终为 0，重启服务无效。

- **门户日志**：只写"任务调用完成"——没有任何异常；
- **真正的错误**：在被调用模块**自己的日志**里，写着"参数校验失败"。

**教训**：**"调用方说成功"不等于"业务成功了"**。要找到**执行业务逻辑的那个模块的日志**，而不是调度方/门户方的日志。

### 第 ④ 步：用 curl 把"网络问题"和"参数问题"分开

```bash
# 先确认地址通不通（只看 HTTP 状态码）
curl -s -o /dev/null -w "%{http_code}\n" https://对端地址/接口

# 再按"旧写法"发一次，看对端怎么回
curl -s -X POST https://对端地址/接口 \
  -H 'Content-Type: application/json' \
  -d '{"业务参数":"xxx","令牌":"yyy"}' -v
```

**判据**：

| 现象 | 指向 |
|---|---|
| 连接被拒 / 超时 | 地址、端口、防火墙、路由 |
| 返回 4xx + "参数错误/鉴权失败" | **传参方式或格式变了** |
| 返回 200 但业务结果异常 | 看业务逻辑或对端数据 |

### 真实根因举例

对端平台升级后，接口从"URL 传参"收紧为 **POST + 表单双参数**（业务参数与令牌必须是**两个独立的表单字段**），而旧代码仍以 **JSON Body** 提交 → 对端直接拒绝。

**修复**：把调用方式由 JSON Body 统一改为表单提交（参数内容不变），多处调用一起改，重启后业务一次性全部恢复。

**沉淀的通用规律**：

> **"重启无效 + 日志无异常 + 业务成果为零" → 查接口传参格式，尤其是对端刚升级过的接口。**

对端升级是这类故障的高发时机。**外部依赖变更后，要把所有调用点一起排查**，而不是只修被报出来的那一处（同一份源码里往往有多处同源调用，属于"留待整改"的隐患）。

## 三、Windows 场景：服务启动超时（错误 1053）

Windows 上的同类问题表现略有不同：

| 现象 | 含义 |
|---|---|
| 启动报 **1053**（服务未及时响应启动请求） | 服务程序在启动阶段**挂住了**（不是崩溃） |
| 事件日志 **7000 / 7009** | 服务启动失败 / 启动超时 |
| 服务列表里"正在运行"，但功能不可用 | 进程起来了、依赖没就绪 |

**排查顺序**：

```
① 进程是否存在        Get-Process 服务进程名
② 服务封装参数        NSSM 封装时看 AppApplication / AppParameters / AppDirectory
③ 启动依赖可达性      程序启动时要连的 DB / 中间件 / 共享目录是否可达
④ 事件日志            事件查看器 → Windows 日志 → 系统（筛 7000/7009）
```

**关键结论**：**1053 多半是"程序在启动阶段等一个够不到的东西"，而不是程序本身有 bug**。所以要先确认它启动时依赖什么（数据库、网络共享、配置文件路径），再去看那个依赖。

**PowerShell 别名陷阱（务必注意）**：PowerShell 里 `sc` 被劫持为 `Set-Content`，用它查服务会**返回空结果而不报错**——非常容易被误导。

```powershell
sc.exe qc 服务名                                   # 正确：显式带 .exe
Get-CimInstance Win32_Service -Filter "Name='服务名'" | Select-Object State,StartMode,PathName
Get-Service 服务名 | Select-Object Status,StartType
```

同类高危别名：`curl`（→ Invoke-WebRequest）、`rm`（→ Remove-Item，参数不同）、`kill` / `sleep` / `ls` / `cat` / `sort` / `select`。
**规则**：给 Windows 的命令，先按目标 shell（PowerShell 还是 CMD）解析一遍，确认不会被别名吞掉；不确定时优先用**原生 cmdlet**。

## 四、数据对不上，先别怀疑链路

**场景**：本方平台与上级平台对**同一批对象、同一时段**的某项报警数量差异明显，双方各执一说，一度怀疑本方转发链路丢数据。

**排查路径（逐层比对，而不是先改配置）**：

```
终端原始上报  →  平台入库记录  →  上报上级的报文
   逐段核对：时间戳、记录条数
   先排除：漏收 / 漏传 / 丢包 / 重复入库
```

**结论**：链路数据**无丢失**。差异全部来自**判定口径**不同——例如"持续超速满 30 秒记 1 次"与"超 30 秒起判、此后每分钟计 1 次"，同一段连续行为被折算成不同次数。

**这次排查最大的价值不是"找到了原因"，而是：**

> **把"数据少了"的技术怀疑（怀疑链路丢数据）与"统计规则差异"彻底分离**，从而**避免误改转发配置造成真故障**。

**方法论固化**：

1. 数量对不上，先把**环节**切开（终端 / 入库 / 上报），逐段核对，确定"哪一段开始不一致"；
2. 在确认链路无丢包**之前**，**不要动转发配置**——链路本身没问题，改配置只会制造新问题；
3. 口径类差异要拉齐三处：**终端阈值、本方平台配置、上级平台口径**；
4. 确认是口径问题后，输出**逐时段比对结论**供双方对齐，把讨论从"谁的系统有问题"转到"用哪个口径"。

## 五、通用检查清单

遇到"重启无效"类问题，按这个顺序过一遍：

- [ ] 服务进程真的在吗？（`systemctl status` / `Get-Process`）
- [ ] 有没有**业务模块自身**的日志？（不要只看门户/调度日志）
- [ ] 用 SQL 按状态字段**分组统计**，确认失败范围（全失败 vs 部分失败）
- [ ] 对端接口**最近是否升级过**？传参方式是否变化？
- [ ] 用 `curl` 手动复现，区分"地址不通"与"传参不对"
- [ ] 同一份代码里是否还有**同源调用**未修？
- [ ] Windows 场景：查事件日志 7000/7009，确认是不是 1053 类启动超时；命令注意 `sc.exe` 别名陷阱
- [ ] 涉及"数量对不上"：先切环节核对，**确认链路无问题前不动转发配置**
