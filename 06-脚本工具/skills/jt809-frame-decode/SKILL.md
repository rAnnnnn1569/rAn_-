# JT/T 809 报文帧解码与定障

## ⚖️ 铁律

1. **先验 CRC，再谈其它**。CRC 不过 = 传输/转义问题；CRC 通过 = 帧完整，问题在**结构**（字段长度、版本口径）或**业务**（结果码）。
   - 判据：`CRC16-CCITT(init 0xFFFF, poly 0x1021)`，覆盖「数据头首字节 → 校验码前一字节」，**大端**存放。
2. **绝不靠"字节数目测"下结论** —— 必须用脚本把 CRC 覆盖区间暴力搜出来，用数据说话。
3. 结论分三级标注：**原文证实 / 实测证实 / 推断**。推断必须写清"还需什么才能定性"。
4. **不确定就向用户确认，不脑补**（对方平台是谁、哪版标准、正常帧长什么样）。

## 帧结构（JT/T 809-2019 表6/表7）

```
头标识 0x5B │ 数据头 29B │ 数据体 nB │ CRC 2B │ 尾标识 0x5D
```

| 字段 | 字节 | 说明 |
|---|---|---|
| MSG_LENGTH | 4 | 数据长度，规范写法=含头标识/数据头/数据体/CRC/尾标识（**实测有平台写成"数据头+数据体+CRC"**，差 2） |
| MSG_SN | 4 | 报文序列号（按子业务类型累加，**断链重连续编不归零**） |
| MSG_ID | 2 | 业务数据类型 |
| MSG_GNSSCENTERID | 4 | 下级平台接入码（上级分配） |
| VERSION_FLAG | 3 | 版本号 Vx.y.z |
| ENCRYPT_KEY | 4 | 加密密钥，0=不加密（**加密只针对数据体**） |
| TIME | 8 | 发送时间 UTC 秒 ← **2019 版新增**，2011 版没有这个字段 |

- 全大端；未使用位置填 0x00。
- 转义：`5B→5A01`、`5A→5A02`、`5D→5E01`、`5E→5E02`（只作用在数据内容上，头/尾标识不转义）。
- 应答类数据体常为 1 字节 RESULT：`0x00`成功 / `0x01`IP 错 / `0x02`接入码错 / `0x03`未注册 / `0x04`密码错 / `0x05`资源紧张 / `0xFF`其他。

```bash
PY="C:/Users/Administrator/.workbuddy/binaries/python/versions/3.13.12/python.exe"
$PY ~/.workbuddy/skills/jt809-frame-decode/scripts/decode809.py "0x5B0000001D...7A5D"
$PY .../decode809.py --header-len 26 "<hex>"   # 换数据头长度假设再试
$PY .../decode809.py --json "<hex>"            # 机器可读，便于批量
# 0x1412「上报报警处理结果」专用（自动补 SPECIFICATION 500B，截断 hex 也能解）
$PY ~/.workbuddy/skills/jt809-frame-decode/scripts/decode1412.py "<hex>" [out.txt]
```

输出里**只看三行**：

| 行 | 含义 | 判读 |
|---|---|---|
| `CRC 自洽` | 帧是否完整 | ✘ → 丢字节/转义没处理；✔ → 帧完整，别往网络上赖 |
| `CRC 命中区间` | 反推出的真实内容边界 | 用于确认内容到底几字节 |
| `差值` | 内容 − 29 | **< 0** → 连数据头都不够，解析必然越界；**= 0** → 数据体为空（应答类必错）；**≥ +1** → 结构正常 |

## 日志报错的对应关系

`System.ArgumentException: 源数组长度不足` + `BinaryHelper.CloneRange → ToUInt32` + `JTB809Parser.<方法名>`：

- 方法名 = `J` + MSG_ID（如 `J1002` → 0x1002 主链路登录应答）→ **先解 MSG_ID 确认是不是这条消息**。
- 该异常 = 解析器按它认定的字段长度读，**读过了数组末尾**。两种根因：
  1. **报文残缺**（对方数据头短、数据体缺失）→ 差值 < 0 或 = 0。
  2. **双方数据头口径不一致**（版本差异；2019 才加 8 字节 TIME）→ 我们的偏移比对方大。
- 区分办法：**拿一条"已知能正常解析"的帧跑同一脚本**。正常帧差值为 +N（N≥1）；若正常帧也报负值，说明是我们解析器的数据头长度假设有问题。

## 已固化案例

| 帧 | 结论 |
|---|---|
| `5B0000001D0000022A10020006E21F0100000000000000003ECAC7BFC07A5D`（2026-09-17，117.159.26.211 河南郑州移动） | 31B；CRC16-CCITT(0xFFFF) 覆盖 27B = **0xC07A**，与日志 `-16262` 一致 → **帧完整**。内容 27B < 数据头 29B → **差值 −2、数据体为空**，而登录应答应有 1B RESULT → 判定**对方报文结构不合规**；J1002 越界读 UInt32 报"源数组长度不足"。字段：MSG_ID 0x1002、MSG_SN 554、接入码 451103、V1.0.0、不加密。MSG_SN=554 若按子业务类型计数 = 反复重连 554 次 |
| `5B0000013000A57C9E1400…884C5D`（2026-09-30，部省「上报车辆报警信息」帧） | ⚠️ **数据头实测 = 30B（不是 29B）**：按 29B 解析数据体首字段得 `0x6F14`（非法），按 30B 得 `0x1402`（正是子业务类型）✓。`MSG_ID=0x1400`（主业务类型「车辆报警信息」），**数据体第 1 个字段 `DATA_TYPE(2B)` 才是子业务类型** → `0x1402` 上报车辆报警信息、`0x1412` 上报报警处理结果。按部省附录表 A.1 逐字段全部对齐（ALARM_ID 恰好 34B、INFO_LENGTH/INFO_CONTENT 自洽）→ 内容可信。**但帧尾 CRC `0x884C` 对不上**（覆盖「头首→校验前」算得 `32F7`；全区间暴力搜索只命中一处 103B 巧合窗口）→ 该 hex 疑在复制/转存中被改动。🔴 **勘误（2026-09-30 复算，先前结论作废）**：当时判「`DATA_LENGTH(264)`、`MSG_LENGTH(304)` 比实际帧少 6 字节、表 A.1 疑有漏行」**是错的**。正确口径：**表 A.1 固定字段合计 254B**（DATA_TYPE 2 + DATA_LENGTH 4 + PLATFORM_ID 11 + WARN_TYPE 2 + WARN_TIME 8 + START_TIME 8 + END_TIME 8 + VEHICLE_NO 21 + COLOR 1 + PLATFORMD_ID 11 + DRV_LINE_ID 4 + ALARM_ID 34 + INFO_LENGTH 4 + START_LAT/LON 4+4 + END_LAT/LON 4+4 + DRIVER 100 + DRIVER_NO 20；不含 INFO_CONTENT），故 `DATA_LENGTH` = 数据体 − 6 = 270 − 6 = **264 ✓**；`MSG_LENGTH` = **全帧长**（含头标识/数据头/数据体/CRC/尾标识）= 1 + **30** + 270 + 2 + 1 = **304 ✓**。两者本身自洽，表 A.1 也没有漏行（序号跳 19、21 只是原文编号跳号）。当时看出"少字节"，真实原因是该 hex 转抄时**漏掉了填充区的 `0x00`** —— `DRIVER` 是 100B 定长全 0，最容易数错。**判据：实到比表长少 N 字节、且缺口落在纯填充区 → 先怀疑转抄漏字，别先怀疑协议。** |
| `5B0000025F0106A0D51400…34165D`（2026-09-30，部省「上报车辆报警处理结果」帧 = 上一条 0x1402 的配套动作） | 数据头(含 5B) = **31B**（= 30B 不含 5B，与上一条一致，两次独立样本把「29 vs 30」钉在 30）。数据体起点偏移 31，`DATA_TYPE=0x1412`、`DATA_LENGTH=567`(=573−6 ✓)、`SOURCE_DATA_TYPE=0x1402` ✓、`VEHICLE_NO=桂J35212`(黄牌 0x02)、`ALARM_ID=4501_0042023986719_D423_1790680181`(恰好 34B)、**`RESULT=0x01` 已处理完毕**、`DEAL_TIME=1790680189`(2026-09-29 19:09:49 北京)、`SPECIFICATION=发送信息`。解析消耗 **573 精确 = 表 A.2 长度** ⇒ 结构自洽。🆕 **DEAL_TIME 距报警开始(1790680181)仅 8 秒** ⇒ 实证"报警进行中即可上报处理"（协议只要求 DEAL_TIME ≥ 开始时间）。⚠️ 本帧为**结构化重建**（用户所贴长 0 串转抄后成奇数长度 → `unhexlify` 失败），只验语义、**未验 CRC** |

## 坑（踩过的）

1. **`-16262` 这类负数 CRC 要先转无符号**：`65536 - 16262 = 0xC07A`，别拿负数直接比。
2. **别看到 CRC 通过就判"对方没问题"** —— CRC 只证明"这些字节没被改"，不证明"这些字节符合结构约定"。对方自算自校验，残缺帧的 CRC 一样是自洽的。
3. **尾标识前 2 字节才是 CRC**；`C0 7A 5D` 不要把 `7A 5D` 当成校验值。
4. **长度字段不足采信**：`MSG_LENGTH` 只能当参考，真实边界要用 CRC 反推（实测有平台语义与规范差 2 字节）。
5. **`TIME` 全 0 是"未填"不是"1970 年"** —— 按 8 字节对齐去找 `TIME` 的位置，是定位数据头边界的锚点。
6. **转义/加密不是默认嫌疑**：先确认内容里有没有 `5A`/`5E` 序列、`ENCRYPT_KEY` 是不是 0，再谈这两项。
7. **数据头 2011 vs 2019 差 8 字节**（TIME 字段），跨厂商对接最容易在这里出偏差。
8. 🔴 **数据头长度不是"读出来就行"，要用数据体首字段自验**：部省（两客一危）实测 **30 字节**，比本 skill 默认的 29 多 1 字节，多出的字节落在 `加密密钥(u[18:22])` 与 `TIME` 之间。**做法：先按 29 试，若数据体首字段落在「已知子业务类型」上（0x1402/0x1412/0x1201/0x120C…）才成立；否则 `--header-len 30` 再试。** 出现 `0x6F14`、`0x6F…` 这类怪值，就是数据头少算了。
9. **「数据体第一个字段 = 子业务类型 DATA_TYPE」**：主业务类型 `0x1400`（UP_WARN_MSG 车辆报警信息）之下，`0x1402`=上报车辆报警信息、`0x1412`=上报车辆报警处理结果。**判断"是不是处理结果"只看这一个字段**——`0x1412` 的数据体里有 `RESULT(1B)`+`DEAL_TIME(8B)`，`0x1402` 没有（它是报警信息本身）。
10. **子业务类型定位法（比数数据头更稳）**：不预设数据头长度，直接在偏移 9~39 里找 `0x1412`/`0x1402` 首次出现，再用**下一个字段能否自洽**验证——`DATA_LENGTH` 应 = `表长−6`（0x1412 的表 A.2 = 573B ⇒ DATA_LENGTH = 567 = 0x237）、`SOURCE_DATA_TYPE` 应 = 0x1402、`ALARM_ID` 应恰好 34B 且含 3 个 `_`、车辆号能按 GBK 读成中文。**四条全中即可确认对齐**，无需纠结数据头内部字段怎么切。
11. **`SPECIFICATION` 是 500B 定长文本**：实到内容后全补 `0x00`；脚本按 `\x00` 截断取字符串。只有"不作处理(0x02)/误报警(0x04)"才强制填原因，"已处理完毕(0x01)"允许自由文本（实测值可能只有几个字，如 `发送信息`）。
12. 🔴 **CRC 覆盖区间不含头标识 `0x5B`**（JT/T 809-2019 §8.2.3 原文：「**从数据头到校验码前**的 CRC16-CCITT 的校验值」）→ 正确算法是 `crc16(data[1:-3])`，**不是** `crc16(data[:-3])`。把 `0x5B` 算进去会全帧校验不过，白白去怀疑对方篡改。（`gx809` 工具 2026-09-30 已按此修正，见案例 A：河南 J1002 帧按 `data[1:-3]` 算出 `0xC07A` 与帧尾一致 ✔）
13. **两个长度字段别搞反**：`MSG_LENGTH` = **全帧长**（含头标识 + 数据头 + 数据体 + CRC + 尾标识）；表 A.1 / A.2 里的 `DATA_LENGTH` = **数据体长度 − 6**（不含 `DATA_TYPE` 与 `DATA_LENGTH` 自身）。表 A.1 固定 **254B** + INFO_CONTENT（最长 1024）；表 A.2 固定 **573B**（含 SPECIFICATION 500B 定长）。
14. **填充区是"数错字节"的重灾区**：`DRIVER(100B)`、`SPECIFICATION(500B)` 多为全 `0x00`。日志 / 聊天 / 工单转抄时最容易漏抄几个 0 → 表现为「实到比表长少 N 字节」。**这属于源数据问题，不是协议问题** —— 应先报「少 N 字节、缺口落在填充区」，而不是判对方报文不合规。（2026-09-30 就因这个误判过一次，见上方勘误）
15. 🔴 **同一个子业务类型 `0x1412`，部省与川标是两张完全不同的表**（2026-09-30 原文核实）——**解码前先问/先判是哪套口径**，否则字段整体错位：
    - **部省**（《两客一危部省交互规范 试行》**附录A.3 节**、内含**表A.2**「主动上报报警处理结果格式」，**573B**）：
      `DATA_TYPE(2)+DATA_LENGTH(4)+SOURCE_DATA_TYPE(2)+VEHICLE_NO(21)+VEHICLE_COLOR(1)+ALARM_ID(34)+RESULT(1)+DEAL_TIME(8)+SPECIFICATION(500)`
    - **川标**（T/SCSDX 0003.4 **表70**）：`VEHICLE_NO(21)+VEHICLE_COLOR(1)+DATA_TYPE(2)+DATA_LENGTH(4)+INFO_ID(32)+RESULT(1)+METHOD(1)+OPERATOR_LENGTH(1)+OPERATOR+COMPANY_LENGTH(1)+COMPANY`
      —— **无 DEAL_TIME(8B)、无 SPECIFICATION(500B)**，且 `DATA_TYPE/DATA_LENGTH` 挪到了第 22~27 字节。
    - 快判：**总长约 573B / 尾部有 500B 填充区 → 部省**；**长度明显更短、末尾是「操作人+单位」变长文本 → 川标**。
    - 🔴 **表号易混**：「上报车辆报警处理结果」是**附录 A.3 这一节**，里面的**表叫 表A.2**。写「表 A.2」= 写「附录 A.3 的表」，别当两个东西（`gx809` 与本 skill 已统一为「部省附录A.3／表A.2」）。
