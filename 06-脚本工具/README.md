# 脚本工具

> 这里放的脚本遵循同一条原则：**自己带安全护栏，不把"运维动作"变成"新的故障源"**。
> 具体体现为：并发锁、空间阈值、`--dry-run` 预演、失败即清理、破坏性操作默认不执行。

## 一、MySQL 备份 / 恢复

详见 [`mysql备份恢复/README.md`](mysql备份恢复/README.md)。核心能力：

- 日备（保留 7 天）+ 周备（保留 21 天）双级全量，凭据走外置配置文件；
- `mysqldump --single-transaction` 一致性快照，不锁表；
- binlog 增量归档（`FLUSH BINARY LOGS` 封口后只归档**已闭合**日志）；
- 被排除大表的**结构补偿**（`--ignore-table` 会连结构一起丢，这是必踩的坑）；
- `sha256` + 退出码 + `Dump completed` 三重完整性校验；
- 一键恢复 / `--stop-datetime` 时间点恢复 / `--dry-run` 预演。

设计说明与踩坑清单见 [`../02-数据库/MySQL备份与恢复体系.md`](../02-数据库/MySQL备份与恢复体系.md)。

## 二、大容量分层分批备份

```bash
# 只抢救配置与程序（最快，通常几十秒到几分钟）
HOST=user@host SRC_BASE=/opt/app bash 大容量分层分批备份.sh ./backup t0

# 先 t0 再全量分批
HOST=user@host SRC_BASE=/opt/app bash 大容量分层分批备份.sh ./backup all
```

**三个设计取舍值得说明**：

1. **分层**：先把"配置 + 程序"捞出来（业务恢复靠它），再去传全量数据。因为大容量传输耗时可能以小时计，**先保证"即使现在断电，我也能重建业务"**。
2. **分批**：按一级子目录切包，某个包传失败只重传那个包，不用从头再来。
3. **不落盘**：压缩放在**源端**做，源机器上不生成中间大文件——**坏道盘上每多写一次都是风险**。

> ⚠️ **源盘有坏道时把 `PARALLEL` 保持为 1**。并行读会加剧坏盘的寻道压力，也可能把坏盘 IO 打满导致别的服务响应变慢。顺序读更安全。

## 三、Windows 双机日志自动打包推送

`Windows日志自动打包推送.ps1.example` —— 源机把业务日志目录压缩后，自动推送到同网段目标机的共享目录。

```cmd
REM 1) 复制模板并改名（.example 只是为了避免带真实路径的实例入库）
copy Windows日志自动打包推送.ps1.example D:\Scripts\push_log_archive.ps1
REM    ⚠️ 另存为 UTF-8 with BOM，否则 PS 5.1 按 GBK 解析中文路径 → 报"源目录不存在"

REM 2) 改脚本里的 <平台目录> / <平台日志目录> / <目标机IP> / <共享名>

REM 3) 先预演（只压缩不传输）
powershell -NoProfile -ExecutionPolicy Bypass -File D:\Scripts\push_log_archive.ps1 -DryRun

REM 4) 注册任务（每天 02:00 触发，脚本内 60 小时闸门 → 实际 2.5 天一次）
schtasks /Create /TN "日志备份推送" /TR "powershell.exe -NoProfile -ExecutionPolicy Bypass -File D:\Scripts\push_log_archive.ps1" /SC DAILY /ST 02:00 /RU <源机服务账号> /RP * /RL HIGHEST /F
```

**五个设计取舍**：

1. **零依赖**——只用 `tar.exe` + `robocopy` + `schtasks`，不装 Python、不装第三方工具。
2. **先压本地再推网络**——压缩过程不直接写网络路径，网络抖动不会污染压缩耗时。
3. **频率靠脚本闸门**——任务计划没有"每 2.5 天"周期（硬设 `/SC HOURLY /MO 60` 会时间漂移），所以"每天 02:00 触发 + 脚本内 60 小时闸门"。
4. **失败不记账**——只在传输成功后写时间戳，失败次日 02:00 自动重试，不会"失败一次等两天半"。
5. **退出码语义**——`robocopy` 的 0~7 全算成功，≥8 才失败；写成 `-ne 0` 会误判。

> 🔴 **最容易踩的是前置条件**：`.ps1` 必须是 **UTF-8 带 BOM**。PowerShell 5.1 对无 BOM 的文件按 ANSI(GBK) 解析，脚本里的中文路径会变乱码，运行时提示"源目录不存在"——**而目录明明就在那儿**。

**SMB 连通排障**（错误 5 / 找不到网络路径 / 445 超时）见 [`../05-故障复盘/Windows双机日志自动推送-SMB连通排障SOP.md`](../05-故障复盘/Windows双机日志自动推送-SMB连通排障SOP.md)，那里按"链路 → 安全组 → 主机防火墙 → 共享名 → 权限"五层给了解法。

## 四、生产配置与运维脚本

[`配置文件与脚本/`](配置文件与脚本/) —— 从真实生产环境整理出来的 9 份配置与脚本。

| 文件 | 看点 |
|---|---|
| `01_nginx-proxy.conf` | 业务反代 + 附件转对象存储，带**按域名防盗链** |
| `02_docker-compose_gateway.yaml` | 代理网关 + JT809 转发器：`network_mode: host`、挂载编译好的 DLL、官方运行时镜像 |
| `03_reachability_check.sh` | 按 **IP 第二段自动选抓包网卡**，再筛 `unreachable` 目标 |
| `04_iptables_forward.sh` | DNAT/SNAT 规则下发：**幂等封装 + 端口变更检测**（`-C` 查重、端口模糊化比对旧规则） |
| `05_url_sign.py` | 接口签名 = `MD5(MD5(pwd) + t)`，生成实时/历史/报警附件三类 URL |
| `06_docker-compose_zabbix.yaml` | zabbix 监控栈编排，口令走 docker secrets |
| `07_zabbix_server.conf` | zabbix_server 主配置全量参数 |
| `08_link_monitor.py` | 链路巡检：**两次采样比对** → 机器人告警 |
| `09_schtasks_link_monitor.sh` | 巡检脚本的 Windows 计划任务注册 |

**为什么值得看**：这几份文件里的取舍都是"在真实约束下做出来的"——
host 网络换来性能却把端口冲突风险推给编排顺序；挂载编译产物省掉整条 CI 却把构建责任转移给宿主机；
`04` 用"端口模糊化比对"化解了"规则要改但线上在跑，直接删会断流"的两难。

> 🔴 **脱敏范围只限两类**：服务器 IP（公网稳定 1:1 映射到 RFC 5737 文档段；私网保留网络段位，因为 `03` 的抓包网卡 dispatch 依赖 IP 第二段）与口令/Token（数据库口令、命令行默认口令、机器人 Webhook UUID）。
> 域名、平台名、容器名、部署路径等**一律保留原样**——这些正是配置文件的可读性所在，换成角色名反而看不出它在干嘛。

## 五、写脚本的几条自定规则

给自己定下的底线，也是"脚本能交给别人跑"的前提：

| 规则 | 为什么 |
|---|---|
| 凭据走外置配置文件（`chmod 600`），不进命令行 | 命令行参数会被 `ps aux` 看到 |
| 破坏性操作默认**不执行**，必须显式确认（`--yes`） | 默认安全的脚本才是好脚本 |
| 提供 `--dry-run` 只打印将执行的命令 | 让人在动手前能看一遍 |
| 失败即清理产物 | 不留"半截备份"误导人 |
| 带并发锁（`flock`） | cron 重入 / 上次未跑完是真实场景 |
| 带空间阈值，不足即中止 | 备份撑爆磁盘会反噬业务 |
| 日志统一落文件并带时间戳 | 出问题时有据可查 |
| `set -euo pipefail`，但 `if` 替代 `[ ] && cmd` | `[ ] && cmd` 在 `set -e` 下条件为假会中断脚本 |

> 最后一条是实测踩出来的：`set -e` 下写 `[ -f "$X" ] && do_something`，当文件不存在时整个脚本会**静默退出**。统一写成 `if [ -f "$X" ]; then do_something; fi` 才稳。
