# 监控告警：三级分流 + 电话叫醒

> 核心问题：**告警太多等于没有告警**。
> 群里刷屏的结果是所有人对告警麻木，真正致命的那一条被淹掉。

---

## 一、为什么必须分级

先看一个常见的失败模式：

```
所有告警 → 全部发到同一个群
        → 每天几百条
        → 值班人不看了
        → 严重告警也是"群里的一条"
        → 深夜无人响应
```

**根因不是"告警不够多"，而是"严重程度没有被区分对待"。** 分级要解决两件事：

1. **不同级别走不同通道**（严重级别要能穿透"静音/免打扰"）；
2. **每个通道只承载它该承载的**（邮件留档、群里可见、电话叫醒）。

---

## 二、三级通道分工

| 级别 | 通道 | 承载范围 | 设计意图 |
|---|---|---|---|
| **全部** | 邮件 | 所有告警 | **留痕留档**，事后可追溯，不追求即时性 |
| **警告及以上** | 飞书机器人卡片 | 警告 / 平均 / 高 / 灾难 | **群内可见 + 带详情**，日常处理主战场 |
| **严重 / 灾难** | **语音电话** | 仅严重与灾难 | **叫醒**，自动播报主机名与级别 |

**关键设计取舍**：

- **电话只承接最高两级**。这是整套方案的成败点——电话一旦被打成"所有告警都打"，就会变成骚扰，值班人会把号码拉黑，通道彻底失效。
- **电话只播报关键信息**（哪个主机、什么级别），详情仍走飞书/邮件。语音播报信息密度低，塞太多内容反而听不清。
- **飞书卡片用交互式卡片**（带颜色区分级别），比纯文本更容易一眼扫到重点。

---

## 三、落地要点

### 3.1 严格限定触发级别

在告警动作（Action）里用**条件**卡死级别门槛：

```
条件：Trigger severity >= High（严重）
```

不要靠"人肉约定"，要靠配置约束——否则某次值班人为省事调低门槛，通道就废了。

### 3.2 去重与维护期

| 问题 | 处理 |
|---|---|
| 同一问题反复告警（抖动/flapping） | 触发器加**恢复表达式**做迟滞（如"低于阈值才恢复"），避免边界值反复横跳 |
| 已知维护窗口 | 配置**维护期（Maintenance）**，维护期内不触发告警 |
| 一个问题引发连环告警 | 用依赖（Dependency）压制下游告警，只报根因 |

### 3.3 成本控制

语音电话走**公共模式按量计费**，单通成本极低（约 0.1 元量级）。真正的成本不是钱，而是**误报导致的信任损耗**——所以宁少勿滥。

## 四、顺带修正的两个告警判据（真实误报根源）

### 4.1 磁盘告警：不要用"使用率百分比"

**问题**：磁盘使用率长期在 88%~95% 波动是**正常态**（例如日志盘按保留天数滚动，`free` 在几 GB 间周期变化）。用"使用率 > 90%"做判据，会**周期性误报**。

**为什么**：使用率是**相对值**，它随盘的总容量变化；一块大盘用了 92% 可能还剩几十 GB，完全安全；一块小盘用了 92% 可能只剩几百 MB，非常危险。

**改成绝对量判据**：

```
last(/主机/vfs.fs.size[/data,free]) < 2G      # 剩余空间低于 2G 才告警
```

> 这条修正的意义不只是"少几条误报"——它把判据从**相对**改成**绝对**，逻辑上更正确。

### 4.2 预测型告警（`timeleft`）用在对的地方

`timeleft()` 的原理是**取最近一段时间的增长斜率做线性外推**，算"照这个速度多久到阈值"：

```
timeleft(/主机/vfs.fs.size[/data,pused],1h,100) < 86400      # 24 小时内会满
```

**它的软肋**：对**脉冲式写入**极度敏感。日志轮转前突然暴涨，斜率瞬间变大，它就算"几小时后满"，但轮转后回落——于是误报。

| 盘的类型 | 是否适合 `timeleft` |
|---|---|
| 平稳增长（数据库数据盘） | ✅ 适合，能提前预警 |
| 周期脉冲（按天/按容量滚动的日志盘） | ❌ 不适合，改用硬阈值 |

**结论**：预测型判据要用在"增长模式可外推"的对象上；对周期性对象，硬阈值更稳。

## 五、一个容易被忽略的点：**服务"进程在"不等于"服务在"**

用 `service.info[...]` 这类监控项判服务状态时，要区分两种失败：

1. **服务没起来**（进程不存在）→ 监控项直接能看出来；
2. **服务起来了但反复重启/启动超时**（进程在、服务不可用）→ 只看"进程存在"会漏判。

**做法**：把状态类监控项和"启动失败事件（如 Windows 事件日志 7000/7009/1053）"结合起来看；Windows 场景下尤其要查**事件日志**而不是只看服务列表。
