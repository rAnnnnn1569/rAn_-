# JT/T 809 平台数据交换 学习笔记

> 记录 **平台 ↔ 平台**（上下级监管/监控平台之间）的数据交换机制理解，**不转载标准原文**。
> 这一册的重点不是"背消息 ID"，而是**两条链路怎么建、断了怎么续、数据少了怎么自证**——这三点直接决定对接类故障能不能一次判准。

---

## 一、它解决什么问题

808 解决"终端 ↔ 平台"，809 解决"平台 ↔ 平台"。典型场景是：企业监控平台要把车辆定位、报警、驾驶员信息**逐级上报**给省级/部级监管平台，反过来接收上级的查岗、督办、换发指令。

一句话概括职责分工：

| 方向 | 谁发起 | 干什么 |
|---|---|---|
| **下级 → 上级**（主链路） | 下级平台主动连上级平台 | 上报定位、注册、报警、驾驶员身份、电子运单、行驶路线 |
| **上级 → 下级**（从链路） | 主链路建成后，**上级反过来连下级** | 下发查岗、督办、拍照/监听/报文、交换定位 |

**关键认知**：809 是**双链路**协议，而且**从链路是上级主动发起的**。这意味着"下级能不能被上级连上"取决于下级在登录时**主动告知自己的服务端 IP 与端口**——这条一旦填错，主链路正常但下行全废，是很隐蔽的故障。

---

## 二、双链路：怎么建、怎么断、怎么判

### 2.1 建立顺序

```
下级平台 ──① 登录请求（含接入码/用户名/密码 + 本机从链路服务 IP:端口）──▶ 上级平台
上级平台 ──② 登录应答（成功 / 失败原因码）──────────────────────────▶ 下级平台
上级平台 ──③ 从链路连接请求（带校验码）────────────────────────────▶ 下级平台
下级平台 ──④ 从链路连接应答 ──────────────────────────────────────▶ 上级平台
```

- 主链路成功建立后，**上级才发起从链路**；顺序不可颠倒。
- 从链路连接请求带一个 `VERIFY_CODE`（登录应答里下发），下级要**校验一致**才回成功——这是防串连的一层设计。

### 2.2 链路保活：判断"是否真断"的硬依据

| 情形 | 规则 |
|---|---|
| 有业务数据往来 | **不需要**额外发心跳（数据本身就是保活） |
| 无业务数据往来 | TCP 客户端侧**每分钟**发一个链路保持请求 |
| 连续 **3 分钟** 未收到对方的保持包 | 判定链路中断，主动断开该链路，另一条**保持正常** |

**运维含义**：判断"链路是不是真的断了"，看的是**比约定心跳更长一段时间内无任何报文**，而不是"好像没数据了"。写入监控时，阈值应当按这个量级设（分钟级），而不是秒级。

### 2.3 断链后的恢复方向

- 主链路断、从链路正常 → **下级**重新发起登录（登录内容与首次一致）；重新登录成功后，**上级不需要重建从链路**。
- 从链路断、主链路正常 → **上级**重新发起从链路连接。
- 两条同时断 → 走完整登录流程重来。

## 三、数据不丢的三道设计（对接对账的底气）

这是 809 最值得掌握的部分：**协议自身就提供了"自证有没有丢数据"的机制**。

### 3.1 序列号：按子业务类型分别编号

- 报文头里的 `MSG_SN` 是发送序列号，**按子业务类型分别编号**，上下级各自独立计数、互不影响。
- 从 0 开始，第一帧起计数，到 4294967295 后归零。
- **断链重连后要"续编"**：链路登录成功后，双方先互发**消息序列号通知**，把断链前各子业务类型的序列号同步过来，后续发送**接着原序列号编**。

**运维含义**：重连后序列号**不连续**就意味着中间有报文没送达——这是判断"有没有丢数据"的第一手依据，比事后比对条数更直接。

### 3.2 补传请求

- 接收方按序列号统计，**发现号有缺失**，立即发**消息补传请求**（指明缺的序列号与子业务类型）。
- 发送方按请求**重传**，且**沿用原始序列号**填入（不是新号）。
- 补传等待超时后重发请求，应答超时按递增公式放大：

```
T(n+1) = T(n) × (N + 1)
```

其中 `T(n)` 为上一次应答超时时间，`N` 为重传次数；应答时间与重传次数由双方约定。

### 3.3 断链期间的数据补报

- 链路中断期间产生的定位信息，**链路恢复后要补发**。
- 断开的判定时刻有明确定义：**无业务数据时**以上次收到对方链路保持应答的时间为准；**有业务数据时**以最后一次完整业务包交互时间为准。

> **一句话总结**：809 不需要你去"猜有没有丢"，它给了**序列号 + 补传请求 + 补报**三层机制。排查"上级说数据少了"，先看序列号是否连续、补传是否被触发并完成——**能在协议层分清"链路丢了"和"口径不同"**。

## 四、登录鉴权：失败原因码是把"网络问题"变"参数问题"的钥匙

上级平台对下级接入做验证，**先在 IP 层、再在账号层**：

1. 先校验请求的 **IP** 是否与约定接入 IP 一致——不一致直接失败；
2. 再校验 **接入码、用户名、密码**，返回对应结果码。

常见结果码语义：

| 结果码 | 含义 | 运维动作 |
|---|---|---|
| `0x00` | 成功 | 继续建从链路 |
| `0x01` | IP 地址不正确 | 上级**白名单未加**本机出口 IP |
| `0x02` | 接入码不正确 | 接入码填错 / 发错对象 |
| `0x03` | 用户没有注册 | 账号未在上级登记 |
| `0x04` | 密码错误 | 凭据不一致 |
| `0x05` | 资源紧张，稍后再连 | 上级侧该接入码已被占用（重复登录） |

**这条最实用**：拿到"上级反馈断链"时，**先看应答码**。`0x01` 是白名单、`0x02/0x03/0x04` 是参数，只有都不是才往网络层查。能省掉大量"是不是我们网络不通"的无效排查。

## 五、报文格式要点

| 项目 | 规定 |
|---|---|
| 头标识 | `0x5B` |
| 尾标识 | `0x5D` |
| 字节序 | 大端（网络字节序） |
| 校验 | **CRC16-CCITT**（生成多项式简记 `0x1021`），范围是**头标识到校验码前** |
| 时间 | 8 字节 UTC |
| 加密标识 | 报文头有位标识是否加密 |

**转义规则**（与 808 的 `0x7D` 体系不同，别混）：

| 原始字节 | 转义为 |
|---|---|
| `0x5B` | `0x5A 0x01` |
| `0x5A` | `0x5A 0x02` |
| `0x5D` | `0x5E 0x01` |
| `0x5E` | `0x5E 0x02` |

> **抓包第一直觉**：看到 `5B ... 5D` 是 809，看到 `7E ... 7E` 是 808。**先定界符、再协议**，能立刻判断这段流量属于哪一层。

## 六、加密：只加密数据体

- 加密**只针对数据体**，数据头不加密。
- 密钥随报文传输（`ENCRYPT_KEY` 字段），**不同报文可用不同密钥**。
- 算法是**伪随机序列与明文逐字节异或**，加解密同一套算法；随机序列由三个常量参数 `M1 / IA1 / IC1` 决定。

**运维含义**：`M1 / IA1 / IC1` 是**上下级之间约定一致的参数**——两边不一致会导致"链路通、登录成功、但数据解不开/校验失败"。排查这类"连上了却没数据"的怪现象，除了账号密码，**别忘了核对加解密参数是否配套**。

## 七、常见故障 → 协议层判据速查

| 现象 | 先查什么（协议层） |
|---|---|
| 主链路建立不了 | 登录应答码：`0x01` 白名单 / `0x02` 接入码 / `0x03` 未注册 / `0x04` 密码 |
| 登录成功但上级下发无反应 | 从链路服务 **IP / 端口**是否在登录请求里填对 |
| 链路时断时续 | 保活判据是**分钟级**（无数据时每分钟心跳、连续 3min 判断），别按秒级阈报误警 |
| 上级说"数据少了" | 先看重连后**序列号是否续编连续**、**补传请求**是否触发并完成 → 分清"链路丢"与"口径不同" |
| 连上了但数据异常/解不开 | 核对 **M1 / IA1 / IC1** 加解密参数两边是否一致 |
| 抓包看不懂 | 先看定界符：`0x5B/0x5D` = 809；校验是 **CRC16-CCITT**，与 808 的累加和不同 |

## 八、与地方规范的关系（以四川为例）

地方标准通常**以国标 809 为基线并做扩展**，而不是另起一套。理解时要能分清"哪部分是国标、哪部分是地方加的"——扩展部分（如音视频、报警附件核查等业务）**只有支持该地方规范的平台才认**，对接时逐平台确认对方按哪一版实现，避免"发了对方不认的消息"。
