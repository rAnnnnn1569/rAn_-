# 车载视频接入内网：1078 的协议约束与三种触发模式

> 场景：客户要求把运油车辆的车载视频（实时 / 历史）接入**其生产内网**，而该内网**只进不出（光闸 / 网闸隔离）**。
> 核心矛盾：**JT/T 1078 视频是「请求—应答」模式，不是"打开就一直推"的直播流**。理解这一点，方案方向就定了。

---

## 一、先纠正一个常见误解：1078 不是持续推流

**任何一方要获取 1078 视频，都必须主动向终端下发 `0x9101`（实时音视频传输请求）**，指令中携带**收流服务器 IP / 端口**。终端收到后，才按指令里指定的地址推送 RTP / PS 码流。

**两条硬性推论**：

1. **不先发 `0x9101`，就永远没有视频流**；
2. **流只会发给指令里指定的那个收流地址** —— 换个接收方，就得重新发一次指令。

⇒ 所以"平台一直推流"这种模式在协议上是不成立的。持续推流意味着**一直有活跃的 `0x9101` 会话**，流量消耗极大。

---

## 二、第二个约束：终端在公网侧，内网够不到它

运油车终端在**移动公网**，808 / 1078 的长连接落在**接入侧平台**（代理网关 / 流转发服务器）。

而客户的视频网关在**内网、隔光闸**，**自身够不到终端**，无法直接对车载终端下发 `0x9101`。

⇒ **只能由公网侧代发指令**，把流导向客户内网的收流地址。

---

## 三、第三个约束：光闸的"单向"到底单到什么程度

这是决定方案可行性的关键前提，**必须先向客户确认**：

| 问题 | 为什么关键 |
|---|---|
| **视频数据单向流入** | 媒体流方向 |
| **信令控制是否允许回流** | **直接决定能否做"按需点播"** |

- 若光闸**只允许媒体单向流入、禁止任何反向信令** → 只能做**常开流**（见模式一）；
- 若允许**控制信令双向往返**（媒体仍单向）→ 可以做**按需点播**（见模式二）。

⚠️ 把"只进不出"直接理解成"完全不能回传任何东西"是常见误判 —— **媒体单向 ≠ 信令单向**，必须问清楚。

---

## 四、三种触发模式

由于 `0x9101` 是**瞬时动作**，必须由业务事件触发。按触发源与光闸能力分三种：

### 模式一：常开流（Always-on）—— 最稳

**做法**：车辆一上线即由公网侧发起 `0x9101`，把流**持续推送到网关收流端口**，网关侧始终有画面。

```
车辆上线事件 / 定时检查
   └→ 接入服务 发 0x9101（收流地址 = 光闸外口 : 网关收流端口）
       └→ 终端推 RTP/PS 流 → 光闸 → 视频网关 → 内网用户
```

| | |
|---|---|
| 触发源 | 定时 / 车辆上线事件（接入侧可控，**无需客户回传信号**） |
| 优点 | 实现最简单；**不依赖光闸信令方向，不依赖网关主动能力** |
| 代价 | 持续占带宽与流资源，车辆越多开销越大 |

**适用**：小规模、对时延敏感、光闸方向不明朗时优先选它。

### 模式二：信令回调触发（按需点播）—— 最省带宽

**做法**：内网侧用户点选"看车 X"→ 通过光闸反向信令（HTTP / 自定义协议）通知公网接入服务 → 收到后**即时**发 `0x9101`，把流终点指向网关收流端口。

```
内网用户点选车辆X
   └→ 客户平台/网关 → 光闸反向信令 → 接入服务
       └→ 发 0x9101（收流地址 = 网关收流端口）→ 终端推流 → 光闸 → 网关
```

| | |
|---|---|
| 触发源 | 内网侧人工点播事件 |
| 优点 | **按需发流，带宽利用高效** |
| 前提 | **光闸必须允许控制信令回流**（媒体仍单向），否则物理上不可行 |

### 模式三：网关主动拉流（供网关本身支持 1078 主动模式时）

**做法**：网关自身点播，直接参与 1078 信令交互。

| | |
|---|---|
| 触发源 | 网关自身点播动作 |
| 优点 | 接入侧最省事 |
| 缺点 | **牵涉上游平台配合开放信令中转，改动最大**；终端需增加网关服务器地址配置 |

### 选择顺序

```
光闸信令方向未确认  →  模式一（常开流），先跑通
光闸允许信令回流    →  升级模式二（按需点播），省带宽
网关自身支持 1078   →  才考虑模式三
```

## 五、客户网关的协议能力，决定后端工作量

| 网关情况 | 需要做的事 |
|---|---|
| **支持 1078 被动收流** | 最优路径：接入侧只做**流终点配置与转发**，复用网关自身的 1078 能力 |
| **仅支持 RTSP / GB28181** | **必须由接入侧提供协议转换**：1078 拉流服务 → 转出 RTSP / GB28181 接入光闸 |

**场景二的实施要点**（以协议转换为例）：

1. 部署 1078 拉流服务（信令 `0x9101` + RTP/PS 接收）；
2. 输出 RTSP / GB28181 接入光闸；
3. 与客户联调光闸方向、网关注册、平台拉流；
4. 上线后回读校验，监控带宽与并发。

---

## 六、必须提前确认的前提清单（0 成本，先做）

- [ ] 客户网关**支持哪种协议**（1078 / RTSP / GB28181），是否支持被动收流
- [ ] 光闸的**信令方向能力**：媒体单向还是双向？控制信令能否回流？
- [ ] 网关的**收流地址与端口**、是否允许多路并发
- [ ] 车辆规模与并发数（测算带宽）
- [ ] 视频进入内网后，接入侧的**运维与回读校验通道**怎么走（内网受限，需提前约定）
- [ ] 上游流转发平台是否可提供**裸流地址接口**（区别于网页播放器 URL）

## 七、风险提示

| 风险 | 说明 |
|---|---|
| **"只进不出"的准确含义** | 务必确认是"视频数据单向流入"还是"任何数据都不可回流"——直接决定能否按需点播 |
| **带宽成本归属** | 网关支持 1078 时，带宽落在一侧；需自建转换时，带宽落在接入服务侧，要提前测算 |
| **合规与运维** | 视频进入客户生产网后，接入侧访问受限，回读校验与运维通道需提前约定 |
| **视频内容安全** | 此类项目**只做路由与转发，不解码、不存储、不修改原始视频**（数据红线） |

---

## 八、从这件事得到的通用教训

**先确认技术前提能不能实现，再谈方案。**

本项目最初的判断偏差在于：把"1078 视频接入"当成了一个**单向推流**的对接问题，而实际上它是**请求—应答**模型，必须由可触达终端的一方主动下发指令。这个前提没确认清楚，方案就会建立在错误假设上。

**通用做法**：任何跨域视频 / 数据对接，先回答三个问题——

1. **数据由谁产生、谁有能力发起**？（本例：终端只被动响应，必须由公网侧发起）
2. **中间隔离设备的策略是什么**？（本例：光闸，且媒体与信令方向可能不同）
3. **对端设备支持哪些协议、能承担哪一半工作**？（本例：决定要不要自建协议转换）
